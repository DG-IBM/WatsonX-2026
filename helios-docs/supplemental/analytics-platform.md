## 1. Platform Overview

The Helios Analytics Platform provides:

1. **Customer-facing analytics** — energy consumption trends, grid reliability metrics, outage analytics, demand forecasting accuracy. Embedded in the customer portal via the Analytics API.
2. **Regulatory reporting** — pre-formatted reports for OFGEM, BDEW, and AEMO submissions. Generated by the Reporting Service.
3. **Internal BI** — operational dashboards for Lumina's own use (Metabase). Tracks product usage, customer health, platform performance.
4. **ML feature store inputs** — pre-computed aggregates used as training data for the AI Forecasting Engine.

## 2. Data Warehouse Architecture

### Redshift Cluster

| Parameter | Value |
|-----------|-------|
| Instance type | ra3.4xlarge (4 nodes) |
| Storage | ~290 TB (Redshift Managed Storage) |
| Region | eu-west-1 (primary), eu-central-1 (DR snapshot) |
| Database | `helios_analytics` |

### Schema Structure

```
helios_analytics/
├── raw/              -- Direct Kafka → S3 → Redshift loads (append-only)
│   ├── raw_grid_readings
│   ├── raw_outage_events
│   └── raw_device_status
├── staging/          -- dbt staging models (lightweight cleaning)
│   ├── stg_grid_readings
│   ├── stg_outage_events
│   └── stg_meters
├── intermediate/     -- dbt intermediate models (business logic)
│   ├── int_demand_aggregates
│   ├── int_reliability_events
│   └── int_meter_performance
├── marts/            -- dbt final marts (customer-facing + internal)
│   ├── mart_customer_consumption
│   ├── mart_grid_reliability
│   ├── mart_outage_analysis
│   ├── mart_device_health
│   └── mart_forecasting_accuracy
└── reporting/        -- Regulatory reporting views
    ├── rpt_ofgem_monthly
    ├── rpt_bdew_quarterly
    └── rpt_aemo_monthly
```

### Loading Strategy

| Source | Mechanism | Frequency | Latency |
|--------|-----------|-----------|---------|
| Kafka → S3 | Kafka Connect S3 Sink | Continuous | ~5 min |
| S3 → Redshift staging | AWS Glue job (COPY) | Every 30 min | ~35 min |
| Redshift staging → dbt | dbt run | Every hour | ~15 min |
| Continuous aggregates from TimescaleDB | pg_dump → S3 → Redshift | Daily (03:00 UTC) | ~1 hour |

**Total data latency (end-to-end, Kafka → analytics API):** ~2 hours typical.

This is acceptable for most analytics use cases (trends, historical analysis) but means the analytics API should not be used for real-time monitoring. For real-time, use the Grid API directly.

## 3. dbt Models

### Model Architecture

dbt models follow the staging → intermediate → mart pattern. All models have documentation in `schema.yml` files and tests (not_null, unique, relationships).

#### Key Staging Models

```sql
-- models/staging/stg_grid_readings.sql
WITH source AS (
    SELECT * FROM {{ source('raw', 'raw_grid_readings') }}
),
renamed AS (
    SELECT
        meter_id::UUID                           AS meter_id,
        customer_id::UUID                        AS customer_id,
        timestamp::TIMESTAMP WITH TIME ZONE      AS reading_timestamp,
        power_kw::DECIMAL(12,4)                  AS power_kw,
        energy_kwh::DECIMAL(12,4)                AS energy_kwh,
        quality_flag::SMALLINT                   AS quality_flag,
        -- Exclude suspect/invalid readings from main aggregations
        CASE WHEN quality_flag <= 1 THEN TRUE ELSE FALSE END AS is_billable,
        loaded_at::TIMESTAMP                     AS _loaded_at
    FROM source
    WHERE timestamp > DATEADD(year, -7, GETDATE())  -- 7-year rolling window
      AND meter_id IS NOT NULL
      AND timestamp IS NOT NULL
)
SELECT * FROM renamed
```

#### Grid Reliability KPIs (SAIDI / SAIFI)

These are regulatory-grade calculations used in OFGEM and BDEW reporting. The formulas were corrected in September 2024 — see [Ravi's note](#analytics-platform) above.

```sql
-- models/intermediate/int_reliability_events.sql
-- SAIDI = System Average Interruption Duration Index
-- SAIDI = SUM(customer interruption durations) / total customers served
-- SAIFI = System Average Interruption Frequency Index  
-- SAIFI = total customer interruptions / total customers served

WITH interruption_events AS (
    SELECT
        o.outage_id,
        o.customer_id,
        o.started_at,
        o.restored_at,
        o.affected_meter_count,
        DATEDIFF(minute, o.started_at, o.restored_at) / 60.0 AS duration_hours,
        -- NOTE(Ravi 2024-09-18): Must use meters_in_service_at_time, not current meter count
        -- This was wrong in v1 of this model and overstated SAIFI/SAIDI
        cs.meters_in_service_at_time
    FROM {{ ref('stg_outage_events') }} o
    JOIN {{ ref('int_customer_meter_counts_historical') }} cs
        ON o.customer_id = cs.customer_id
        AND DATE_TRUNC('month', o.started_at) = cs.month
    WHERE o.restored_at IS NOT NULL  -- Exclude active outages
),
monthly_aggregation AS (
    SELECT
        customer_id,
        DATE_TRUNC('month', started_at) AS month,
        SUM(affected_meter_count * duration_hours) AS total_interruption_hours,
        SUM(affected_meter_count) AS total_interruptions,
        MAX(meters_in_service_at_time) AS meters_in_service
    FROM interruption_events
    GROUP BY customer_id, DATE_TRUNC('month', started_at)
)
SELECT
    customer_id,
    month,
    total_interruption_hours / meters_in_service AS saidi_hours,
    total_interruptions::FLOAT / meters_in_service AS saifi,
    meters_in_service
FROM monthly_aggregation
```

### dbt CI/CD

As of Q3 2024, dbt models are validated in CI before merging:

```yaml
# .github/workflows/dbt-ci.yml
name: dbt CI
on: [pull_request]
jobs:
  dbt-compile-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install dbt
        run: pip install dbt-redshift==1.7.3
      - name: dbt compile (syntax check)
        run: dbt compile --profiles-dir ./.dbt --target ci
      - name: dbt test (schema tests only — no full run in CI)
        run: dbt test --select tag:schema_test --profiles-dir ./.dbt --target ci
```

The `ci` target points to a staging Redshift schema, so schema tests run against a small representative dataset rather than the full production warehouse.

| Device Availability | % of devices reporting within expected interval | `mart_device_health` |
| Renewable Generation % | Share of energy from renewable sources | `mart_customer_consumption` |

### Metric Calculation: Demand vs. Forecast Accuracy

The forecasting accuracy metric is critical — our contracts with some customers include accuracy SLAs.

```sql
-- mart_forecasting_accuracy.sql
SELECT
    fa.customer_id,
    fa.forecast_run_at,
    fa.horizon_hours,
    DATE_TRUNC('day', fa.forecast_period_start) AS forecast_date,
    AVG(ABS(fa.forecast_mw - ga.actual_demand_mw)) AS mae_mw,
    AVG(
        ABS(fa.forecast_mw - ga.actual_demand_mw) / NULLIF(ga.actual_demand_mw, 0)
    ) * 100 AS mape_pct,
    SQRT(AVG(POWER(fa.forecast_mw - ga.actual_demand_mw, 2))) AS rmse_mw
FROM {{ ref('stg_forecast_outputs') }} fa
JOIN {{ ref('int_demand_aggregates') }} ga
    ON fa.customer_id = ga.customer_id
    AND fa.forecast_timestamp = ga.time_bucket
WHERE fa.horizon_hours BETWEEN 1 AND 48
GROUP BY 1, 2, 3, 4
```

## 5. Customer-Facing Analytics API

The Analytics API is a Node.js service (part of `helios-api`) that exposes pre-computed Redshift mart data to the customer portal.

**Base URL:** `https://api.helios.lumina.energy/v3/analytics`

### Key Endpoints

```
GET /v3/analytics/consumption
  Query params: customer_id, meter_ids[], start_date, end_date, resolution (15min|1h|1d|1w|1mo)
  Returns: Time-series of energy consumption

GET /v3/analytics/reliability
  Query params: customer_id, start_date, end_date
  Returns: SAIDI, SAIFI, CAIDI, outage count

GET /v3/analytics/forecasting-accuracy
  Query params: customer_id, start_date, end_date, horizon_hours
  Returns: MAE, MAPE, RMSE by day

GET /v3/analytics/outages
  Query params: customer_id, start_date, end_date, severity[]
  Returns: Outage events with duration, affected meters, cause category

GET /v3/analytics/export
  Query params: customer_id, report_type (consumption|reliability|outages), format (csv|json), ...
  Returns: 202 Accepted + job_id; poll GET /v3/analytics/export/{job_id} for completion
```

### Caching

Analytics API responses are cached in Redis with TTLs depending on data recency:

```typescript
// analytics-api/src/cache-policy.ts
export function getCacheTTL(
  resolution: TimeResolution,
  endDate: Date
): number {
  const dataAge = Date.now() - endDate.getTime();
  const oneDayMs = 86_400_000;

  if (dataAge < oneDayMs) {
    // Recent data — short TTL, it may update as dbt runs
    return resolution === '15min' ? 300 : 900;  // 5–15 minutes
  } else if (dataAge < 30 * oneDayMs) {
    // Last 30 days — medium TTL
    return 3600;  // 1 hour
  } else {
    // Historical data — long TTL, it won't change
    return 86400;  // 24 hours
  }
}
```

## 7. Reporting Service

The Reporting Service generates scheduled regulatory reports and on-demand customer reports. It's a Node.js service that queries Redshift and produces PDF or CSV output.

**Regulatory reports:**

| Report | Recipient | Frequency | Format | Delivery |
|--------|-----------|-----------|--------|----------|
| OFGEM Monthly Network Performance | Customer (for their OFGEM submission) | Monthly (by 10th of following month) | PDF | Email + portal download |
| BDEW Quarterly Security Report | Customer | Quarterly | PDF | Email + portal |
| AEMO Monthly Performance | Customer (Ausgrid, AusNet) | Monthly | CSV + PDF | SFTP + portal |

```typescript
// reporting-service/src/generators/ofgem-monthly.ts
export async function generateOFGEMMonthlyReport(
  customerId: string,
  reportMonth: Date
): Promise<ReportArtifact> {
  const [reliability, consumption, outages] = await Promise.all([
    getReliabilityMetrics(customerId, reportMonth),
    getConsumptionSummary(customerId, reportMonth),
    getOutageDetails(customerId, reportMonth),
  ]);

  const reportData: OFGEMReport = {
    reportingPeriod: formatReportingPeriod(reportMonth),
    licenseeId: await getLicenseeId(customerId),
    saidi: reliability.saidiHours,
    saifi: reliability.saifi,
    ci: outages.customerInterruptions,
    ces: outages.customerMinutesLost,
    numberOfOutages: outages.total,
    longestOutageDuration: outages.maxDurationMinutes,
  };

  return renderPDF(ofgemMonthlyTemplate, reportData);
}
```

## 9. Known Limitations & Tech Debt

### Current Limitations

1. **2-hour analytics latency** — the data pipeline has ~2-hour end-to-end latency from meter reading to analytics availability. Some customers have asked for near-real-time analytics. Currently not supported.

2. **No customer self-service query interface** — customers can only query via our pre-built endpoints and dashboards. A few enterprise customers (particularly TransnetBW) have asked for a SQL query interface. Not currently on the roadmap.

3. **Redshift costs scaling with customer count** — Redshift is not partitioned by customer, so a complex query from one customer scans all customers' data (with RLS filtering). This is an architectural concern as we scale. Tracked in technical debt.

4. **dbt run failures are not automatically alerting** — if a dbt model fails, the error is logged but no PagerDuty alert fires. This has caused analytics data to silently be stale for several hours in two incidents. Fix: INFRA-2790 (open, assigned to Ravi).

5. **Historical data in Redshift vs. TimescaleDB discrepancy** — data in Redshift may differ slightly from TimescaleDB for recent periods (before the daily full sync). This is by design but causes confusion when customers see different numbers in different views. We need clearer documentation of this in the portal.
